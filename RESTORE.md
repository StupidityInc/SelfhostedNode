# Homelab stacks restore procedure (restic)

This file lives inside every backup of `/opt/stacks/`.
It is the self-describing recovery story for this node, written for the
post-WP5 layout (lobaro container is the primary backup; the host-native
systemd path is an opt-in addon).

## What is backed up

- The entire `/opt/stacks/` directory.
- All service folders (`docker-compose.yml`, `.env`, data bind mounts).
- This `RESTORE.md` and the backup tooling under `_backup/`.

Docker images are **not** backed up (they are re-pulled on restore).

What is **not** in the backup and must be restored from your password
manager or regenerated on the new node:

| Path | Source |
|------|--------|
| `/etc/restic/env` | Password manager (S3 creds + `RESTIC_REPOSITORY`). |
| `/etc/restic/env.docker` | Regenerated by `setup-restic.sh` from `/etc/restic/env`. |
| `/etc/restic/password` | Password manager (or a recovery key temporarily). |
| `/etc/restic/repo-id` | Password manager (32-char lowercase hex UUID, pinned at setup). |
| `/etc/restic/recovery-key.present` | Optional marker — regenerated by `setup-restic.sh` if you re-record a recovery key. |
| `/opt/homelab/env-file/tailscale.env` | **Node-local SSOT** — regenerated by `update-tailscale-ip.sh` after Tailscale is up on the new node. |
| `/etc/homelab/node.env` | Regenerated by `bootstrap.sh` from the persisted run args. |

## Prerequisites

1. A fresh Linux machine (Ubuntu Server recommended).
2. The S3-compatible credentials for this node's repository.
3. The restic repository password (or the separate recovery key, if you
   made one).
4. The 32-char hex `repo-id` pin that `setup-restic.sh` recorded on the
   original node (find it in your password manager or on the original
   node at `/etc/restic/repo-id`).
5. Network access to the S3 endpoint (direct or via a Tailscale exit
   node — see step 0).
6. The original node name. It is **immutable** — `bootstrap.sh` will
   refuse to run with a different name.

## 0. Break-glass: S3 is only reachable via a Tailscale exit node

Some clients have no direct route to the S3 endpoint by design. If a
plain HTTPS connection to the endpoint fails on the replacement machine,
do this **FIRST**, before touching restic:

```bash
# 1. Install Tailscale
curl -fsSL https://tailscale.com/install.sh | sudo sh

# 2. Join the tailnet (interactive login URL, or an auth key)
sudo tailscale up --hostname=restore-temp

# 3. Route internet via your exit node (name or 100.x IP of a server node)
sudo tailscale set --exit-node=<exit-node-name> --exit-node-allow-lan-access=true

# 4. Prove the path works before continuing
curl -4 -s --max-time 10 https://ifconfig.me          # should show the EXIT NODE's public IP
curl -4 -s --max-time 10 -o /dev/null -w '%{http_code}\n' https://<your-s3-endpoint-host>

# 5. If the exit node does not work (not approved? offline?), roll back cleanly:
sudo tailscale set --exit-node=
```

Only continue with the steps below once step 4 succeeds. After the
restore, the full `bootstrap.sh` re-run will set the exit node up
permanently (and the temporary `restore-temp` hostname can be cleaned up
later).

## 1. Install restic and place secrets first

```bash
sudo apt update
sudo apt install -y restic
# or download the official binary from https://github.com/restic/restic/releases
```

Before running `bootstrap.sh` or its restic setup helper, recreate the
secrets directory and place this node's existing `/etc/restic/` artifacts
from your password manager. They are intentionally **not** inside the
stacks backup (secrets live outside the backed-up tree, per
`AGENT.md §2 Backup`).

```bash
sudo install -d -m 700 /etc/restic

# S3 credentials + repository URL + RESTIC_PASSWORD_FILE + cache dir
sudo install -o root -g root -m 600 /path/from/password-manager/env  /etc/restic/env

# The repository password (one line, no trailing newline issues — restic handles it)
sudo install -o root -g root -m 600 /path/from/password-manager/password /etc/restic/password

# Pinned repository UUID — 32 lowercase hex characters.
# A mismatch with `restic cat config --json` is a HARD error (see step 2).
sudo install -o root -g root -m 644 /path/from/password-manager/repo-id /etc/restic/repo-id
```

If the main password is lost, the recovery password can temporarily be
placed at `/etc/restic/password` for the bootstrap/restore, then replaced
with the main password after the node is working. **Do not** leave a
recovery key on disk as the permanent node password.

## 1b. Verify the repository and the repo-id pin

Before touching `bootstrap.sh`, prove the secrets are coherent and the
repository is reachable:

```bash
# In a root shell, source the safe loader and exercise restic:
sudo bash -c '
  source /opt/stacks/_backup/lib.sh
  homelab_load_restic_env /etc/restic/env
  restic snapshots --latest 1
'

# Verify the pinned repo-id matches the live repository.
# If the live id cannot be read (network? credentials?), this is a WARN,
# not a FAIL — but a *mismatch* is a HARD error.
sudo bash -c '
  source /opt/stacks/_backup/lib.sh
  homelab_assert_repo_id_pinned
'
```

`homelab_assert_repo_id_pinned` is the same check that `check-node.sh`
runs as part of the daily health check. If it fails here, do not
proceed — the restored repository UUID does not match the `repo-id` you
placed, which means either the wrong `repo-id` is in the password
manager, or you have connected to the wrong bucket/prefix.

## 2. Verify the repository

```bash
# In a root shell, export the values from the restored /etc/restic/env:
export AWS_ACCESS_KEY_ID="..."
export AWS_SECRET_ACCESS_KEY="..."
export AWS_DEFAULT_REGION="auto"
export RESTIC_REPOSITORY="s3:https://<endpoint>/<bucket>/<node-prefix>"
export RESTIC_PASSWORD_FILE=/etc/restic/password

restic snapshots
restic check
```

A successful `restic check` proves the data on S3 is consistent. It
**does not** prove the node is restored — that requires the steps
below.

## 3. Restore the latest snapshot

```bash
mkdir -p /tmp/restore
restic restore latest --target /tmp/restore
```

To restore a specific snapshot:

```bash
restic snapshots          # note the ID
restic restore <ID> --target /tmp/restore
```

After the restore, `/tmp/restore/opt/stacks/` contains the entire stacks
tree, including the lobaro Compose project at
`/tmp/restore/opt/stacks/restic-backup/` and the host-side
`/tmp/restore/opt/stacks/_backup/` (which contains this `RESTORE.md`,
`check-node.sh`, `lib.sh`, and the dormant `backup.sh`).

## 4. Place the stacks on the new machine

```bash
sudo mkdir -p /opt/stacks
sudo cp -a /tmp/restore/opt/stacks/. /opt/stacks/
```

`cp -a` preserves the ownership and permissions captured in the backup.
Do **not** recursively change ownership on restored stack data; it can
break service users and silently damage the restored ownership model.
The lobaro container's UID/GID must match what the original node used.

## 5. Re-bootstrap the host

Run the current `bootstrap.sh` with the **same role and same node name**
so that Docker, firewall, Tailscale, and base packages exist. The
already-placed restic files must be present before this step so the
wizard keeps the existing repository:

```bash
sudo ./bootstrap.sh --role=<server-or-client> --node-name=<original-node-name>
```

`bootstrap.sh` will detect `/etc/restic/env` and `setup-restic.sh`
will skip credential re-entry, regenerate `/etc/restic/env.docker`
(raw format for Compose `env_file:`), re-pin `repo-id`, then bring the
lobaro container up. The first backup window is async — do not block on
it; `check-node.sh` will surface a stale snapshot if needed.

Then:

```bash
# Make sure the user is in the docker group
sudo usermod -aG docker "$USER"
# log out / log in or newgrp docker
```

If the main repository password was temporarily replaced by a recovery
key, replace `/etc/restic/password` with the main password now and keep
the recovery key offline. If the main password is lost, use the recovery
key you stored offline during setup:

```bash
# Point restic at a file containing the recovery password instead:
export RESTIC_PASSWORD_FILE=/path/to/recovery-password-file
restic snapshots    # works with any valid key, including recovery keys
restic key list     # shows all keys on the repository
```

A recovery key is deliberately **not** stored on any node. If you have
neither the main password nor a recovery key, the repository is
unrecoverable — that is the point of client-side encryption.

## 5a. Regenerate the Tailscale IP SSOT

`/opt/homelab/env-file/tailscale.env` is a **node-local** single source
of truth. It is not backed up; it is regenerated on every node by an
update-timer that watches Tailscale.

`bootstrap.sh` step 3a copies `/opt/stacks/_system/update-tailscale-ip.sh`
into place, installs the `tailscaled.service.d/override.conf` drop-in,
and enables `update-tailscale-ip.timer` (every 15 minutes). After
Tailscale is `up`, the writer runs once and populates the file.

To confirm:

```bash
ls -la /opt/homelab/env-file/tailscale.env
cat  /opt/homelab/env-file/tailscale.env
sudo systemctl status update-tailscale-ip.timer
sudo systemctl list-timers update-tailscale-ip.timer
sudo /opt/stacks/_backup/check-node.sh   # the "Tailscale IP SSOT" PASS line confirms
```

The file MUST hold a valid `100.64.0.0/10` CGNAT IPv4. If it is empty or
holds a stale value, wait one timer tick (`OnCalendar=*:0/15`), or force
a manual run:

```bash
sudo /opt/stacks/_system/update-tailscale-ip.sh
```

Stacks that bind a port to the Tailscale address consume this file via
`env_file:` or `--env-file`, never via a stack `.env` mutation (see
`README.md` → "Tailscale IP SSOT").

## 6. Start services

```bash
# Start the lobaro backup container (already configured by bootstrap step 6).
sudo docker compose --env-file /opt/stacks/restic-backup/.env \
  -f /opt/stacks/restic-backup/docker-compose.yml up -d
sudo docker ps --filter name=restic-backup      # must show 'running'
sudo docker logs restic-backup --tail 50         # visible cron output

# Other stacks (one Compose project per directory under /opt/stacks/):
for d in /opt/stacks/*/; do
  case "$(basename "$d")" in
    _backup|_system|_addons) continue ;;
  esac
  ( cd "$d" && sudo docker compose pull && sudo docker compose up -d )
done
```

If any non-backup stack binds a port and depends on the Tailscale IP
file, the docker compose invocation will fail loudly with
`TAILSCALE_IP missing`. Confirm step 5a succeeded, then retry.

## 7. Verify health

```bash
sudo /opt/stacks/_backup/check-node.sh
```

A healthy restored node reports (at minimum):

- Tailscale: `running` and the IP matches the SSOT file.
- Tailscale IP SSOT: PASS line with the IP.
- UFW: `active`, public SSH lockdown consistent with `KEEP_PUBLIC_SSH`,
  `tailscale0` allowed.
- Restic backup: `lobaro` path active, `restic-backup` container
  running, `repo-id` matches live repository, newest snapshot within
  `STALE_HOURS` (default 36).
- Docker: daemon reachable, no `0.0.0.0`/`::` published ports on
  unintended stacks.

A non-zero exit means at least one FAIL line above. Warnings (WARN) are
informational; they do not affect the exit code (the host-native
mutual-exclusivity WARN during a WP7 migration window is one such
case).

## Notes

- `.env` files are restored as normal files. They were only encrypted
  while inside the restic repository.
- The backup tooling (`_backup/check-node.sh`, `_backup/lib.sh`,
  `_backup/change-restic-password.sh`) is restored and runs against the
  post-WP5 layout (lobaro primary, Tailscale IP SSOT, `repo-id` pin).
- **`/opt/stacks/_backup/backup.sh` and `restic-backup.{service,timer}`
  are present on disk but dormant.** WP2 stopped installing the
  host-native systemd path by default; WP5 removed the dead-copy from
  the bootstrap script. The restored `_backup/backup.sh` is not auto-
  enabled. To re-enable the host-native restic path on this node, run
  `sudo /path/to/repo/addons/restic-host-native/install.sh` after
  `bootstrap.sh` completes. The addon refuses while the lobaro
  container is running (mutual exclusion is one-way at install time,
  `setup-restic.sh` prints a WARN when the host-native timer is
  enabled at lobaro deploy time).
- `/opt/homelab/env-file/tailscale.env` is **node-local** and
  **regenerated**, not restored. Backup tools do not include it.
- For a brand-new node, prefer running the full `bootstrap.sh` from
  the private repo that contains these helpers.
- If this node normally uses a Tailscale exit node, restore network
  connectivity first or the S3 restore will fail.
- The lobaro image runs cron in **UTC** (`CronTimeZone=UTC`); the
  `BACKUP_CRON` line in `/opt/stacks/restic-backup/docker-compose.yml`
  is a UTC expression. Operators in non-UTC timezones must remember
  this when interpreting the schedule.
- **Migrating an existing host-native node to lobaro**: this file
  describes the post-restoration world (lobaro-primary). For an existing
  node that is still on the host-native systemd path (restic-backup.timer
  + `/opt/stacks/_backup/backup.sh`), the one-shot migration is
  documented in `MIGRATION.md` and driven by `migrate-to-lobaro.sh`.
  The migration preserves existing snapshots, is idempotent
  (re-running on an already-migrated node is a no-op exit 0), and the
  exact rollback recipe is in `MIGRATION.md`.
